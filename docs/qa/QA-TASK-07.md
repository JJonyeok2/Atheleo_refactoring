## 뒤 Task 쓰임 관점 검토 (08, 15, 52)
- 시간 창 경계: 차이가 정확히 windowMs면 빠짐. Spec 발췌 규칙(`<`)과 일치하고 테스트로 고정됨.
- 같은 타임스탬프: 허용되고 둘 다 평균에 들어감. 같은 프레임을 두 번 넣는 호출이 있으면 그 값의 가중치가 커지므로 TASK-15는 프레임당 한 번만 add 해야 함(현재 계약상 문제 아님).
- 역행: 마지막으로 **저장된** 유한 값의 타임스탬프와 비교한다. NaN 프레임의 타임스탬프는 기억하지 않으므로 `add(1,100) → add(NaN,200) → add(2,150)`은 예외 없이 통과한다. 프레임 타임스탬프가 단조 증가하는 정상 흐름에서는 영향 없음. 비어 있을 때는 어떤 타임스탬프도 허용되므로 reset 후 0부터 다시 넣는 TASK-52 흐름과 맞음.
- 유한하지 않은 값: 버려지면 창도 밀리지 않는다. 즉 `add(10,0) → add(NaN,1000)`은 10을 돌려주며, 포즈 유실이 길어도 마지막 평균이 유지된다. Task 규칙("현재 평균을 돌려준다")대로이지만, TASK-08/15에서 긴 유실 후 오래된 평균으로 상태 전이를 판정하지 않도록 유실 처리(reset 등)는 호출하는 쪽 책임으로 남는다. 푸터에 기록함.
- reset 뒤: entries와 합계 모두 비워 첫 add가 그 값 그대로 반환됨(테스트 있음).
- 합계 오차: 큐가 1개가 될 때 합계를 다시 맞춰 누적 오차를 끊음. 각도 범위(0~180)와 double 정밀도에서 실사용 문제 없음.

### Impl 판단 평가: 역행 검사를 NaN 검사보다 먼저
- 타당하다. 타임스탬프 순서는 값의 유효성과 별개인 호출 계약이므로, 값이 NaN이어도 역행이면 바로 드러나는 편이 호출 쪽 버그(일시정지 후 reset 누락 등)를 일찍 잡는다. 반대 순서면 NaN 프레임에서 역행이 조용히 넘어가 나중 프레임에서 엉뚱하게 터진다.
- 한계: 위에 적었듯 NaN 프레임 자체의 타임스탬프는 기준에 들어가지 않는다. 이 동작과 "역행 + NaN이면 예외" 동작을 고정하는 테스트는 없다(아래 권고).
